## 2. 产品定位与明确不做

### 2.1 定位（引自 `docs/plans/2026-08-27-followup-roadmap.md`）

AT Nacos 是**面向日常开发/联调场景的 IDE 内 Nacos 工作台**，不是 Nacos 控制台的替代品。
核心用户旅程是：在编辑器里看配置、比配置、改配置、发配置；看服务、摘流量、恢复流量；
让 AI Agent（经 MCP）安全地读取 Nacos 状态。运维视角的集群管理、权限治理不在射程内。

### 2.2 永久非目标（不要在任何 Phase 里"顺手"做掉）

以下各项在 roadmap 中被显式列为不做，理由概述如下，后续 Agent 遇到相关"缺口"时应直接跳过：

1. **权限/用户/角色管理（Console 的 Authority 模块）**——属于运维治理，控制台已有完整 UI，
   IDE 内做半套只会造成越权错觉。
2. **Raft/集群运维写操作**（leader 切换、节点下线等）——`listClusterNodes()` /
   `getServerMetrics()`（`src/nacos/driver/NacosDriver.ts:240-241`，main@c4cc4bf）提供只读
   视图即为上限。
3. **配置 zip 批量导入/导出与同步**——Phase D 的 D4 只做"导出单条配置到文件"，
   zip 明确延后且大概率永不做；批量迁移请用控制台或 nacos 官方工具。
4. **publishOnSave（Ctrl+S 即发布）**——这是 1–8 批次里 opt#2 专门**拆除**的行为
   （见 4.2），任何"提效"提案都不得恢复它。
5. **服务树 `listServices` 带 group 过滤**——1.x 服务列表接口的 groupName 过滤语义跨版本
   不一致，服务树的分组是客户端聚合的（`ServiceTreeProvider` 拉全页后按 `service.group`
   过滤，opt@5d8d6f2 `src/tree/ServiceTreeProvider.ts:240`），不改为服务端过滤。
6. **MCP 写工具默认开启**——D2 做的是"双闸门"（实例级 `allowBackgroundAccess` +
   工具级确认），默认永远只读；`src/mcp/toolCatalog.ts` 里 13 个工具全部 `risk: 'read'`
   是现状也是默认态。

客户端构建链路（main@c4cc4bf `src/extension.ts:89-113`）：
`new NacosHttpClient` → `createAuthStrategy`（可能发登录请求）→ `withAuth` 包装 →
`probeServerState`（打 `/state`，带凭据）→ `resolveConsoleBaseUrl` → `buildDriverChain` →
`new NacosCapabilityResolver` → `new NacosClient`。**即：新建一个客户端至少 2–4 个 HTTP
往返**（登录 + probe + 可能的 console 探测），这是第 5 节所有"客户端复用"话题的成本基准。

### 3.2 硬规则（改代码前必须知道）

1. **`src/nacos`、`src/agent`、`src/mcp` 不 import `vscode`**，仅有两个被豁免的 UI 粘合件：
   `src/nacos/createInteractiveCertVerifier.ts`（交互式 TOFU 弹窗必然依赖 vscode）与
   `src/mcp/hubSync.ts`（写 IDE 的 MCP 配置文件）。用
   `git grep -l "from 'vscode'" -- src/nacos src/mcp src/agent` 验证过，main@c4cc4bf 上只有
   这两个文件。新代码不得增加豁免。
2. **命名空间参数名按 flavor 分发**：`namespaceParamName(flavor, module)` 返回
   `'tenant' | 'namespaceId'`（main@c4cc4bf `src/nacos/driver/normalize.ts:53`）。
   配置模块 v1/v2 用 `tenant`，v3 用 `namespaceId`；不要在任何调用点写死。
3. **默认命名空间跨版本不同**：1.x/2.x 是空串 `''`，3.x 是字面量 `'public'`
   （`normalize.ts:11` 注释 + `:35` `return majorVersion >= 3 ? 'public' : ''`）。
   原样透传，永不归一化。
4. **写操作的编码铁律**（main@c4cc4bf `src/nacos/driver/writes.ts`）：
   - 发布 = `POST` + **form**（`x-www-form-urlencoded`），never JSON body（`writes.ts:14-35`，
     注释解释了 Spring `@RequestParam` 只认 query 和 form）。
   - 删除 = `DELETE` + **query string**（`writes.ts:53-71`，servlet 容器只为 POST 解析 form body）。
   - 实例更新 = `PUT` + form，**整行覆盖**：`updateInstanceHealthAt`（`writes.ts:97-122`）
     把 `ip/port/clusterName/enabled/healthy/ephemeral/weight/metadata` 全部回填。
     **这意味着 Phase C1（权重/元数据编辑）复用同一条 PUT，只是改动不同字段**；
     任何"只发送变化字段"的想法都是错的，会把其它字段重置为服务端默认值。
5. **没有 rollback 端点**：`NacosDriver.ts:253-263`（main@c4cc4bf）明确注释——回滚 = 读历史
   版本 + 以当前 dataId 重新 publish，产生**新的**历史行。回滚语义只能在确认对话框层解释。
6. **404 的二义性已被处理**：`describeConfigFailure`（`NacosDriver.ts:478-484`，main@c4cc4bf）
   把"404 且不是 Spring 错误页"分类为 `resource-not-found`（配置不存在），其余走
   `classifyHttpStatus`（可能是端点不存在 → 触发 driver 链回退）。opt#4 的"新建配置"
   正是踩在这个分类上：`resource-not-found` → 空草稿（见 4.4）。
7. **响应体上限**：`MAX_CONFIG_BYTES = 128KB`（`NacosDriver.ts:290`）、
   `MAX_LIST_RESPONSE_BYTES = 4MB`（`:296`）、`listResponseCap(pageSize)`（`:318-320`）。
   注意这只覆盖**配置列表**路径（`fetchConfigPage` 在 `:345-348` 传了
   `maxResponseBytes`）；`fetchConfigDetail`（`:410-425`）**没传**——这是 B5 的由来（见 5.7）。
8. **只读实例是双层防线**：树层用 contextValue 变体隐藏写菜单
   （`src/tree/NacosTreeItems.ts:41-48` `contextValueFor` 返回 `atNacos.<kind>.readonly`），
   写编排层 `confirmWrite` 再拒一次；driver 层刻意不知道只读概念
   （`NacosDriver.ts:208-213` 注释）。改菜单 when 表达式时别打破第一层。
9. **TLS TOFU**：`NacosHttpClient` 的 `attachCertVerification`（main@c4cc4bf
   `src/nacos/NacosHttpClient.ts:354-392`）在证书校验期间挂起响应，
   `pauseInactivityTimeout`（`:395-428`）在交互式弹窗期间暂停 socket 空闲超时。
   交互式 verifier 只应存在于 UI 路径；MCP/后台路径必须用非交互 verifier
   （`NacosAgentToolService.ts:196-203`，main@c4cc4bf 已经构造了它，但 main 的组合根
   把它丢掉了——见 4.8）。
10. **客户端池按指纹失效**：`NacosClientPool.getClient`（`src/nacos/NacosClientPool.ts:39-59`）
    对比连接相关字段的指纹，变了就重建；`evict(instanceId)`（`:65`）与 `clear()`（`:69`）
    在 main 上就都存在——1–8 的 opt#1 只是**改了调用方**，没改池本身。

### 3.3 两个虚拟文档 scheme

- `nacos:`（`NacosConfigDocumentProvider`，main@c4cc4bf `src/document/NacosConfigDocumentProvider.ts`）

## 4. 1–8 项优化批次：问题、证据、落地状态

> 状态标记：**已落地@opt** = 在 `5d8d6f2`（`origin/cursor/nacos-opt-1-8-6a9b`）上已实现并有测试；

### 4.1 opt#1 写路径不再 `clientPool.clear()`；改为定向刷新

- **症状（main）**：`src/extension.ts:178-182`（main@c4cc4bf）
  ```ts
  const refreshTreeViews = (): void => {
    clientPool.clear();
    configTreeProvider.refresh();
    serviceTreeProvider.refresh();
  };
  ```
  所有写完成回调都指到它：发布（`:645`、`:689`）、回滚（`:491`）、删除（`:732`）、
  实例上下线（`:758`、`:785`）、实例表单保存（`:202`）、实例管理（`:275`）。
- **为什么要紧**：`clear()` 丢掉**所有**实例的已登录、已 probe 的客户端。按 3.1 的成本基准，
  下一次两棵树重绘时每个实例都要重付 2–4 个 HTTP 往返（登录+probe+console 解析）；
  且一次配置发布会连服务树一起重绘，纯属浪费。配了 5 个实例的用户每发布一次配置，
  背后是 10–20 个多余请求。
- **1–8 分支改了什么**（opt@5d8d6f2 `src/extension.ts`）：
  - `:190` `refreshAfterConfigWrite`（只刷配置树，不动池）、`:193` `refreshAfterServiceWrite`、
    `:203-205` `refreshAfterInstanceChange(instanceId?)`（只 `clientPool.evict(instanceId)`
    定点驱逐——`evict` 在 main 的 `NacosClientPool.ts:65` 本来就有，只是没人用）。
  - 调用方逐一改指向：回滚 `:594`、发布 `:793`、删除 `:855` → config；
    实例上下线 `:881`、`:908` → service；实例表单/删除实例 `:229`、`:307`、`:346` → instance。
  - **保留**了两处 `clientPool.clear()`：`:369-376` 的 `atNacos.refreshConfigs` /
    `atNacos.refreshServices` 标题栏手动刷新按钮——这是故意的逃生舱（用户主动点刷新
    = 想要全新状态），不要"顺手优化"掉。
- **检测**：`grep -n "refreshAfterConfigWrite" src/extension.ts` 有输出即已落地。

### 4.2 opt#2 Ctrl+S 与发布解耦（`nacos-draft:` 保存只落本地）

- **症状（main）**：`src/extension.ts:658-703`（main@c4cc4bf）。`saveDocumentListener`
  监听 `onDidSaveTextDocument`，对脏草稿**直接调用 `publishConfig`**（`:683-689`），
  用 `inFlightPublish: Set<string>`（`:658`）防重入。
- **为什么要紧**：Ctrl+S 是肌肉记忆。虽然 `publishConfig` 内部仍有 diff 预览+确认对话框，
  但"保存一个还没改完的草稿"就被拽进发布流程本身就是错误的心智模型；确认框一旦被
  习惯性回车，就是一次误发布。roadmap 已把 publishOnSave 列为永久非目标（2.2 第 4 条）。
- **1–8 分支改了什么**（opt@5d8d6f2 `src/extension.ts:805-826`）：监听器保留（仍过滤
  scheme + `isDirty`），但**不再调用 publishConfig**，改为 5 秒状态栏提示：
  ```ts
  vscode.window.setStatusBarMessage(
    t('Draft saved locally. Run "Publish" to send {dataId} to Nacos.', ...), 5000
  );
  ```

## 5. 性能分析（1–8 之后仍存在的问题）

> 排序原则：P0 = 正确性问题伪装成性能问题，或对每个用户每天可感；
> P1 = 特定但常见场景下显著；P2 = 打磨。每项标注对应 Phase 任务。
> 除特别注明外，以下问题在 main@c4cc4bf 与 opt@5d8d6f2 上**同样存在**（1–8 没碰这些文件）。

### 5.1 【P0】Bridge 逐 chunk `toString('utf8')` —— 多字节字符可被劈坏（B2）

`src/mcp/BridgeServer.ts:404-412`（main@c4cc4bf，opt 相同）：

```ts
for await (const chunk of request) {
  const buffer = Buffer.isBuffer(chunk) ? chunk : Buffer.from(chunk);
  bytesReceived += buffer.length;
  if (bytesReceived > BRIDGE_MAX_BODY_BYTES) { exceeded = true; break; }
  body += buffer.toString('utf8');
}
```

TCP 分包不看字符边界。一个中文字符（UTF-8 三字节）跨 chunk 边界时，两次 `toString('utf8')`
各产生一个 U+FFFD 替换符，JSON 解析随之失败或者——更糟——**静默把中文配置内容写坏**
（MCP 写工具落地后这就是数据损坏）。次要问题是 `body +=` 的 O(n²) 字符串拼接。
修法是收集 `Buffer[]` 最后 `Buffer.concat(...).toString('utf8')`，见 **Phase B Task B2**。
定级 P0 的理由：这是正确性 bug，且中文用户（本产品主要受众）必然触发条件。

### 5.2 【P0】超时与页大小硬编码，无任何用户设置（B1）

现状没有 `contributes.configuration`（main/opt 的 package.json 都没有该节）。硬编码点：

- 请求超时：`DEFAULT_TIMEOUT_MS`（`src/nacos/NacosHttpClient.ts:271` 引用处，main@c4cc4bf）；
- 配置树页大小：`CONFIG_PAGE_SIZE = 100`（`src/tree/ConfigTreeProvider.ts:34`）；
- 历史页大小：`HISTORY_PAGE_SIZE = 100`（`src/webview/ConfigHistoryPanel.ts:23`）。

慢网/大命名空间用户没有任何调节手段。**Phase B Task B1**。

### 5.3 【P1】MCP 每次工具调用重建客户端（B6）

见 4.8(b) 的"代价"。opt@5d8d6f2 `src/extension.ts:267-268` 的工厂每次调用
`createNacosClient` = 每个 MCP 工具调用付出登录+probe（2–4 个 HTTP 往返，通常
数百 ms）。一个 AI Agent 的多步会话（列命名空间 → 列配置 → 读配置 → 读历史）
把这个成本乘以 4。**Phase B Task B6**（MCP 独立客户端池：按指纹缓存 +
非交互 verifier，绝不与 UI 池共享）。main 上此问题以另一种形态存在（共享 UI 池，
快但会弹窗挂死，见 4.8），所以无论哪条基线 B6 都成立。

### 5.4 【P1】3.x 实例/订阅者列表在 100 处静默截断（B7）

### 5.5 【P1】`nacos:` 文档 provider 零缓存；跨环境对比双倍拉取（B4）

`src/document/NacosConfigDocumentProvider.ts`（main@c4cc4bf）：

### 5.6 【P1】GET 无幂等重试：keep-alive 复用 socket 的 `ECONNRESET` 直接冒泡（B3）

`NacosHttpClient.performRequest`（main@c4cc4bf `src/nacos/NacosHttpClient.ts:224-331`）

"随机报错，再点一次就好"。GET 幂等，重试一次是安全的。**Phase B Task B3**。

**Phase B Task B5**（客户端级默认 4MB，特殊路径显式覆盖）。

opt#8 只改了并行，没改 `catch(() => [])` / `catch(() => undefined)`

### 6.5 矩阵的三个结论

1. **读侧基本打平控制台**：13 个 MCP 工具与 Driver 的 13 个读方法一一对应
   （`toolCatalog.ts:25-144` ↔ `NacosDriver.ts:217-241`），UI 读侧的洞只有三个：
   服务详情面板（A7）、按 IP 反查监听（A8）、历史翻页/互比（A6）。
2. **写侧的洞全在"编辑既有资源的细粒度字段"**：权重/元数据（C1）、tags/描述（C4）、
   命名空间 CRUD（C3）、克隆（C2）——driver 的写原语（form/query/整行覆盖）都在，
   缺的是 UI 编排。
3. **两条独立的高危线**：AK/SK（D1，签名算法+密钥存储）与 MCP 写（D2，权限模型），
   各自独立 PR，不与任何其它任务混编。

## 7. UX 分析

### 7.1 l10n 重复键（A2）

`l10n/bundle.l10n.zh-cn.json`（main@c4cc4bf；opt 上未修）共 216 个条目、**214 个唯一键**：

- `"Version"` 出现两次：`:93` → `"版本"`，`:117` → `"版本号"`。JSON 解析取后者，
  于是**所有** `t('Version')` 调用点（历史面板的版本列、集群面板的版本字段）
  都渲染"版本号"，第一个翻译是死代码。两个调用点语境不同（历史条目的"版本" vs
  服务端软件"版本号"），正确修法是拆成两个不同的英文源键——A2 的方案就是这么定的。
- `"Delete"` 出现两次：`:46` 与 `:174`，译文相同（`"删除"`），运行期无害，
  但说明**没有重复键检查**。A2 附带加一个 lint 测试防回归。

### 7.2 README 与实现不符（A1；opt#5 只修了 AK/SK 一条）

逐条对照 main@c4cc4bf 的 `README.md`（除第 1 条外，opt@5d8d6f2 上**原样保留**）：

| README 行 | 宣称 | 实际 | 证据 |
| --- | --- | --- | --- |
| `:15` | 支持 AK/SK 签名鉴权 | 直接 throw | `createAuthStrategy.ts:31-35`；**opt 已修**（4.5） |
| `:23` | 智能识别 `TOML` | 后缀表里**没有 toml** | `configLanguage.ts:6-11`（yaml/yml/properties/json/xml/html） |
| `:39` | "发布时校验服务端 MD5" | 是**全文对比**，非 MD5 | `src/write/publishConfig.ts:49-59`（`draft.baseContent !== serverContent`） |
| `:77`、`:115` | "1890 单元测试" | 静态计数 main=1431 / opt=1487（1.3 节） | `git grep -E "^\s*(it\|test)\(" <sha> -- "*.test.ts"` |
| `:115` | "100% 覆盖率保证" | 仓库无覆盖率脚本/门禁 | package.json scripts 无 coverage（A14 补脚本，A1 改措辞） |
| `:14` | "跨版本全兼容……3.x" | 3.x 无真机验证 | `NacosDriver.ts:314-316` 注释自认 "Unverified: no 3.x server has been available to this project" |

A1 的原则：删数字、删绝对化形容词，改为可验证的事实句。

### 7.3 命令面板不可达（A3）

main@c4cc4bf 的 `contributes.menus.commandPalette` 13 项**全部** `"when": "false"`——
这对 `openConfig`/`loadMoreConfigs` 这类必须有树上下文的命令是正确的，但
`atNacos.publishConfig` 也在其中：一个打开着脏草稿的用户在命令面板里搜 "publish"
什么都搜不到，而 opt#2 之后状态栏提示让用户"执行「发布」"，却没告诉他去哪执行
（右键树节点或编辑器标题栏）。A3 = 让 `publishConfig` 在活动编辑器是 `nacos-draft:`
时可从命令面板调用。

### 7.4 错误节点是死胡同（A4）

树加载失败渲染 `ErrorTreeItem`（main@c4cc4bf `src/tree/NacosTreeItems.ts:441-457`，
`contextValue = 'atNacos.error'`），但 package.json 没有任何菜单挂在这个 contextValue 上
——错误信息在 description 里能看到（`:444-446` 注释），可用户唯一的恢复手段是
标题栏全量刷新（顺带 `clientPool.clear()`，5.10）。A4 = 错误节点挂"重试"菜单，
定向重载失败的那个节点。

### 7.5 连接测试的失败解释全是英文（A5）

`src/nacos/testNacosConnection.ts`（main@c4cc4bf）`describeConnectionFailure` 的
每个分支都是硬编码英文长句且未包 `t()`：`:315`（error）、`:321`（address）、
`:330`（gateway 401 长解释）、`:335`（tls）等。这些恰恰是新手最需要读懂的文案
（诊断质量本身很高——比如 401 分支正确指出"Nacos 本身从不返回 401，是网关在拒绝"）。
同类问题：`NacosClient.ts:112`（main@c4cc4bf）的 v3 admin 403 建议也是硬编码英文。
A5 = 全部收进 l10n。

### 7.6 标题栏塞了 10–12 个图标（A9）

`view/title` 在 main 上 10 项、opt 上 12 项（1.3 节），两棵树各 5–6 个：
add/refresh/filter/clearFilter/clusterStatus/manageInstances 几乎全量平铺。
`openClusterStatus` 与 `manageInstances` 在两棵树上重复出现（main@c4cc4bf package.json
view/title 表）。A9 = 低频项收进 `navigation` 之外的溢出组（`...` 菜单）。

### 7.7 术语：「实例」一词两用（A12）

`NacosInstanceConfig`（扩展里配置的一条 Nacos **连接**）与 Nacos 领域里的服务**实例**
（`NacosInstance`，一个注册的 ip:port）共用中文"实例"。树里同时出现"实例节点"
（连接）与"服务实例节点"（ip:port），`atNacos.manageInstances` 管理的是前者。
A12 = 面向用户的文案统一改为「连接」vs「服务实例」，代码标识符不动。

### 7.8 webview 一律 `lang="en"`（A13）

`src/webview/html.ts:34`（main@c4cc4bf）硬编码 `<html lang="en">`，而内容经 l10n
渲染成中文——屏幕阅读器与浏览器排版按英文处理。A13 = 从 `vscode.env.language` 透传。

### 7.9 只读状态在深层节点不可见（A11）

只读徽记只挂在实例根节点（main@c4cc4bf `NacosTreeItems.ts:111-114`，
`description = t('read-only')`）；深层配置节点靠 contextValue 变体（`:41-48`）
**静默隐藏**写菜单。用户在第三层右键一条配置发现没有"发布"，没有任何解释为什么。
A11 = 深层节点 tooltip/描述提示只读来源。

### 7.10 脏草稿不可发现（B9）

草稿只活在内存 FS（3.3）。窗口里开着五个改了没发布的草稿，没有任何列表能看到
"哪些改了还没发布"；关窗即失。B9 = "列出脏草稿 / 丢弃草稿"命令。
（放在 Phase B 是因为主要工作在 draft FS provider 的枚举接口。）

### 7.11 历史：一页 100 条、只能与当前比（A6）

证据在 6.1 表：`ConfigHistoryPanel.ts:23`（`HISTORY_PAGE_SIZE = 100`）、`:185`
（写死 `pageNo: 1`）、`:64`（"diff of one version against the current content"）。
Driver 的 `listConfigHistory` 本来就分页、`getConfigHistory` 返回与 `getConfig` 同型
（`NacosDriver.ts:220-227`）——翻页与任意两版本互比是纯 UI 工作。A6。

### 7.12 保存 vs 发布的心智模型（opt#2 修复后的余量）

- **1–8 前**：Ctrl+S = 触发发布流程（4.2），最危险的形态。
- **1–8 后**：Ctrl+S = 本地保存 + 状态栏提示。余量问题：提示指向的"发布"入口
  不在命令面板（7.3 / A3）；脏草稿列表缺失（7.10 / B9）。两个任务落地后此模型闭环。

### 7.13 集群面板的 CPU/内存是裸小数（A10）

`ClusterStatusPanel.ts:349-351`（main@c4cc4bf）渲染 `metrics.cpu` / `metrics.mem`，
`formatNumber`（`:390-391`）输出 `toFixed(4)` 的裸数——用户看到 `0.3333` 而不是 `33.3%`。
A10 = 按百分比渲染并保留原值 tooltip。

### 7.14 实例表单（opt#3 修复后的余量）

表单保活已修（4.3）。余量：表单没有 AK/SK 选项（与 D1 绑定，D1 落地时一起加）；
连接测试失败文案英文（7.5 / A5）。
